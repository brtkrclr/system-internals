Processes, Visualized

Spawn processes, poke at a task_struct, randomize an address space, grow a process tree, fork with copy-on-write, and step through execve.

4.1Program vs Process

A program is a file on disk. A process is a running instance of it. Run the same file several times.

📄 /usr/bin/sleep
one ELF file, one inode

Every process gets its own PID, address space (randomized by ASLR), fd table and state. The code pages of sleep and libc are shared through the page cache, so the program's code is in RAM only once.

Connection: the shared code pages come from the page cache (6.7) via file-backed mappings (6.6).

4.2task_struct: Click a Field

Every process and every thread has its own task_struct. Almost every other topic is one of its fields and what that field points to.

Connection: /proc/<pid>/status is generated on the spot from this struct (7.10); current gives the one running on this CPU.

4.3Process Image: Memory + Execution Context

The memory image stays in place while a process is paused. The CPU registers don't: they're saved into the kernel's record and restored later. Preempt the process and watch.

Simplified: the user registers are actually saved on the task's kernel stack (struct pt_regs), and task_struct->thread keeps the kernel stack pointer and FPU state. Either way, they belong to this task until it runs again.

Connection: this save/restore is the context switch of 3.5; task_struct points to the image but does not contain it.

4.4Process Memory Layout and ASLR

From high addresses (top) to low. Randomize the layout, grow the heap, make a big allocation, and recurse until the stack overflows.

Addresses are illustrative but follow the real shape: PIE binary near 0x55…, libraries near 0x7f…, stack near 0x7ffc…, kernel in the upper half.

Connection: each row is a VMA (6.4); heap growth is brk(), big mallocs are mmap() (6.6); the stack overflow is a page fault outside any VMA → SIGSEGV (6.5).

4.6Priority and Niceness

Nice values map to weights; CPU time is shared in proportion to weight. Each step is about 1.25×.

Two CPU-bound tasks on one core. Regular users may only raise niceness; lowering it needs root or CAP_SYS_NICE.

Connection: these are the same weights the scheduler uses to grow vruntime (3.6).

Static vs dynamic linking: libc code in RAM

Illustrative sizes: assume each program uses about 1 MB of libc code. Dynamic linking maps the same page-cache pages into every process; static linking copies the code into each binary.

Connection: LOAD segments become VMAs with page-table permissions (6.3, 6.4); GNU_STACK makes the stack non-executable (2.7); PIE makes ASLR possible (4.4).
